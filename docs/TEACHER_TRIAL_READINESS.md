# 发给老师之前：内部就绪与交接

用户决定：先完善平台，再由用户向老师发送试用。本文是内部准备，不是已发出的邀请、不是真实教师评价，也不是减负实验已通过。

后续校园 LAN 方案已获确认：见[当前负责人交接](verification/2026-10-19/teacher-trial/README.md)和[内部验收](verification/2026-10-19/teacher-trial/VERIFICATION.md)。已建立独立演示账号、数据库和非敏感合成样例，仅开放人工流程，不开放模型/远程仓库/执行。下方综合要求尚不能全勾选，尤其异机访问与真实教师实验仍未通过。

## 本次内部默认旅程

先验证“课程作业”的一条连续旅程：教师建立任务并发布 → 学生准备固定成果并提交 → 教师核对源码与候选（AI 可选）→ 修改、确认并发布评价 → 学生读取并提交改进版本。

开放项目与模板验收继续保留，只有实际试用需要时才加入老师的首轮任务，避免一开始同时引入所有路径。最终试用范围仍由用户与老师确认。

## 内部验收

- [ ] 固定源码版本、入口、运行时和已知限制可定位，重要成果有可恢复副本。
- [ ] 正常师生流程使用隔离测试资料真实走通，权限、版本、源码和发布内容一致。
- [ ] 未配置模型时仍可提交和人工反馈；AI 外发、费用和接收方需明确确认，不回退平台共享密钥。
- [ ] 登录/退出、超时/失败/未知结果、重复点击、旧版本与页面返回均有对应回归，不丢草稿或重复计费。
- [ ] 待办、任务说明、当前判断和源码依据容易找到，桌面/窄屏与键盘主流程按声明范围通过。
- [ ] 备份、恢复、账号和资料授权按实际访问方式核对；开发演示不直接变成公网任意代码执行服务。
- [ ] 老师实际使用的电脑能访问目标地址；访问开发机、独立部署与公网部署分别说明，不混淆。
- [ ] 试用样本获准使用，账号口令通过合适私下渠道交接，不写入公开说明或演示。

勾选只能依据本轮证据。未做真机/系统读屏/生产环境验证的项应明确未覆盖，不能用自动化替代。

## 准备交给老师的最小材料

1. 一份短说明：本次体验的任务、正确入口、账号获得方式和已知限制，不附密钥。
2. 一组获准示例：任务目标、固定代码版本、可核对证据与预期体验路径；原始学生资料另需授权。
3. 一个明确反馈入口：记录具体卡点、误判、难懂的说明和额外复核负担，不要求老师只给好评。
4. 故障退路：无法连接、模型失败和退出结果未确认时的处理方式；保留人工路径和原资料。

本轮不发送邀请、不打开公网端口；用户后来确认校园 LAN 方案后，已建立独立演示账号，仅用于非敏感试用。私下交接账号和异机验收按上方负责人清单进行。

## 后续怎样验证减负

先区分首次可用性试用与减负对照实验。看页面后的口头喜欢，不足以证明节时；熟悉同一个样本后的第二次更快，也不能直接算平台效果。

正式实验前确认同源样本、不同模式的输入、老师接触过的资料、顺序、发布终点、授权和费用预算。计时到老师形成可发布反馈，分别记录准备、等待、阅读、修订和发布；失败与无新增价值的结果进入分母。

现有 [H/R/S/A 协议](EVALUATION.md) 和[课程逐条评阅协议](../eval/coursework-evaluation-protocol.md)可复用，不在内部就绪时虚构教师、样本或节时阈值。新评审包的分数保持空，正式试用后再填写。

内部目标是“适合交给老师试用”，后续目标才是“证明在哪些任务下确实减少净负担”。两种状态必须分开。
