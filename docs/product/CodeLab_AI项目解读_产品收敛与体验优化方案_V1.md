# 知因 CodeLab｜AI 项目解读产品收敛与体验优化方案 V1

> 核心主张：带着源码证据，讲清一个项目是怎么工作的。
>
> 不再让用户操作一套复杂的分析工具，而是帮助用户完成一次有依据的项目阅读。

初稿日期：2026-10-14；方案复核：2026-10-17  
状态：产品目标与验收基准；仓库已有部分实现，不代表全量验收或上线  
范围：项目导入、分析确认、分析过程、报告阅读、源码联动、失败恢复  
适用人员：产品、设计、前后端开发、测试、答辩演示人员

阅读建议：产品决策先看第 1、4、7 章；开发排期看第 9、10 章；测试和发布看第 11～14 章。本文是优化方案，不是完成报告；代码中存在某项能力，不等于运行实例已更新或真实用户验收通过。

---

## 1. 决策摘要

本次优化不推翻分析引擎，不新增一套聊天产品，不把教学平台改成通用代码审计工具。重点是重新组织已有能力，让价值比参数更早出现。

建议优先做四件事：

1. **收敛主流程**：导入项目 → 确认费用并开始解读 → 阅读有证据的报告。
2. **确立一个视觉中心**：围绕核心业务场景解释项目，并可直接定位同版源码。
3. **降低决策负担**：首次按需配置模型，默认提供基础解读，高级选项折叠；保存源码仍独立于付费分析。
4. **把可靠性纳入体验**：局部补查失败不等于全部成果作废，但必须明确受限范围，不能假装完整成功。

建议模块导航名称从“AI 项目分析”改为 **“AI 项目解读”**。保留内部接口和技术命名，先调整用户可见名称。原因是本模块首先解决“理解项目”，不是承诺漏洞审计、自动评分或运行验收。

产品一句话：

> 上传项目，沿着核心业务找到实现它的代码。

全平台仍以实训任务和师生交流为教学主线；本模块作为可独立使用的项目阅读工具，在阅读完成后自然连接实训，不强制先加入课程。

### 1.1 一页决策：先交付什么

| 决策 | 首个可发布版本 | 后续版本／明确不承诺 |
| --- | --- | --- |
| 核心价值 | 一段业务解释、一个核心场景、可点击的同版源码证据 | 不承诺理解整个仓库或证明项目运行正确 |
| 用户操作 | 导入 → 明确确认费用 → 阅读报告 | 不让用户先理解调查轮次、反证和格式修复 |
| 主要界面 | 我的项目、一个确认面板、三项阅读导航 | 不新增独立聊天中心或多层地图导航 |
| 视觉特色 | 场景说明与证据紧密联动，选中与返回位置稳定 | 结构化有向链路通过语义评测后独立开放 |
| 失败处理 | 已有结果可保留、限制可解释、历史可读、重连不重复收费 | 不通过吞掉关键错误制造“分析成功” |
| 发布判断 | 真实入口可用、费用明确、证据同版、故障可恢复 | 不以构建通过或一次模型成功替代验收 |

**优先级冲突时的取舍：真实性与费用安全 > 主流程可靠 > 阅读清晰 > 图形丰富度。** 若需要压缩范围，先推迟复杂链路，不削减历史阅读、受限提示和付费确认。

## 2. 依据、现状与边界

### 2.1 本方案依据

- 用户反馈：功能冗杂、重点特色不突出，连续失败影响使用体验。
- 用户此前反馈的故障现象：选择 ZIP 不符合预期、项目反复分析失败。选择器覆盖、计划格式、运行版本和端口冲突列为排查方向；本方案不将未经本轮复现的历史原因作为当前故障定论。
- 本次检查的实现：`Projects.vue`、`SourceProjectReport.vue`、`SourceProjectMap.vue`、`project-map.ts`、源码分析契约。
- 与既有《教学闭环与体验升级方案 V2》的方向保持兼容：AI 提供导读与证据，教师保留最终评价权，不把静态分析包装成运行验收。

本方案没有开展新的用户访谈或完整视觉验收。后文的指标、尺寸和默认策略是待验证的设计目标，不是现有测量结果。

**阅读说明：** 下文“当前”描述主要用于记录优化起点，不表示所有旧界面仍然存在。2026-10-14 文档复核时，仓库已存在三标签报告、场景阅读组件及可选链路生成开关等部分实现；因此实施时应先做差距核查，复用已完成能力，不重复建设。实现进展另见[实施验收记录](AI项目解读_实施验收记录.md)，其中历史记录也须与最新代码和测试证据核对，不能代替上线验收。

### 2.2 已有能力与真正缺口

| 领域 | 当前代码中已存在 | 优化重点 |
| --- | --- | --- |
| 项目导入 | ZIP、文件夹打包、仅保存、保存并分析 | 减少同屏并列操作，明确保存与付费边界 |
| 分析确认 | 模型、模式、目录范围、费用、版本比较 | 按需披露，不让首次用户理解所有配置 |
| 报告阅读 | 项目概览、模块与链路、问题、学习路线 | 重排阅读主线，避免摘要和地图重复导航 |
| 项目地图 | 全局地图、业务场景、阅读路线、文件树 | 从默认展开的大地图转向任务明确的场景阅读 |
| 源码证据 | 引用位置、源码查看、已读范围 | 让“结论 → 证据 → 返回原位置”形成稳定闭环 |
| 分析详情 | 调查过程、用量、费用、覆盖率、错误 | 合并技术入口，保留关键提醒，减少外露 |
| 容错 | 已有计划解析、报告校验和错误处理入口 | 核实本地规范与受限降级实际行为，补齐真实接口及运行版本验收 |

**重要约束：当前项目地图的模块关系来自“共同引用了同一个文件”，不是真实调用图。** `project-map.ts` 已明确这一点。不能仅把连线换成箭头，就将其宣传为函数调用链。

现有报告的 `flows` 是标题、正文和引用组成的场景说明，不包含完整的有序步骤及步骤之间的调用依据。因此“核心业务链路”分两期实现：先做可靠的场景说明与证据联动，再引入有结构、有校验的链路数据。

### 2.3 2026-10-17 差距复核：复用已有实现，补齐验证

本次只读核对了项目入口、报告组件、质量字段契约及关系验证器。以下是代码层面的定位，不作为正式环境验收结论；已有测试结果详见实施记录，本次文档整理没有重新执行这些测试。

| 方案项 | 仓库可见实现 | 下一步重点 |
| --- | --- | --- |
| 导入后确认 | “保存并继续”“仅保存源码”和独立高级选项已存在 | 验证真实文件选择器、保存不收费、配置后回到原流程 |
| 阅读主线 | 三标签、`CoreScenarioReader`、前三阅读入口已存在 | 用陌生项目测试是否真正找得到依据，不继续增加主导航 |
| 受限质量 | 契约已有 `reportQuality`、原因代码及旧报告兼容分类 | 核对列表、历史、统计与正式服务口径，未知不算完整 |
| 结构化链路 | 可选 `EvidenceFlowReader` 和生成开关已存在 | 开启前完成关系语义评测，旧报告继续使用场景说明 |
| 调用依据 | 关系验证器采用保守的同文件 JS／TS 命名函数直接调用识别 | 不宣称跨文件、跨语言、动态调用或数据流已获通用验证 |
| 实测材料 | 实施记录记载合成样本和自动化回归 | 补独立真实项目评阅、真实参与者试测及目标实例验收 |

因此，后续排期以第 10 章工作包的实际缺口为准，不能把已有功能当作全新开发重新计时，也不能把尚未完成的验证直接勾选通过。

## 3. 用户、任务与价值定位

### 3.1 主用户与任务

| 用户 | 进入页面时的问题 | 最小有效结果 |
| --- | --- | --- |
| 学生／项目作者 | 我该如何理解和讲清自己的实现？ | 能描述项目用途、沿一个场景找到关键代码 |
| 教师／评阅者 | 这个作品的核心实现在哪里，有什么值得追问？ | 快速找到业务依据和少量待核实问题 |
| 同伴阅读者 | 我能从这个项目学什么？ | 一条可执行的阅读路线和对应源码 |

主任务不是“完成一轮 Agent 调用”，而是：**用户能带着证据解释一条核心业务。**

### 3.2 对外特色只强调三项

1. **讲清业务**：不是只列技术栈，而是解释项目服务谁、解决什么问题。
2. **直达源码**：解释附带同版文件与行号，可以核对，不依赖盲信 AI。
3. **指导阅读**：告诉用户先读哪里、关注什么、哪些内容仍不确定。

不作为首页卖点：多轮调查、模型数量、Token 统计、复杂图谱、自动安全审计、泛化聊天能力。

## 4. 信息架构：三个页面任务，一条阅读主线

```text
AI 项目解读
├─ 我的项目：找到旧项目 / 导入新项目
├─ 项目详情
│  ├─ 尚无报告：开始解读 / 查看源码
│  ├─ 分析中：当前阶段 / 停止 / 离开后返回
│  └─ 报告：读懂项目 → 看核心场景 → 定位证据
└─ 辅助入口：分析详情 / 历史报告 / 高级设置 / 关联实训
```

保留现有 `/projects`、`/projects/:id` 路由，不为每个视图新增一级导航。

### 4.1 首页：我的项目 + 导入

- 空状态：主标题“从一份项目开始，读懂它的实现”，一个上传区域、一句价值说明。
- 有项目：已有项目列表优先，新建入口固定在标题区；不要求老用户每次滚过大型宣传区。
- 上传区保留“选择 ZIP”和“选择文件夹”，两者是文件获取方式，不是两个竞争的业务流程。
- 选中文件后显示名称、大小、移除／更换；主按钮“保存并继续”，次级文字操作“仅保存源码”。
- “保存并继续”只导入并进入确认步骤，不暗中开始付费调用。旁边明确说明“下一步确认模型与费用，当前不会调用 AI”。
- 导入失败保留选择与可恢复状态，说明具体原因；无需用户重新理解整套入口。
- 项目条目只显示：名称、导入时间、报告状态、最近一次解读时间。文件数等信息进入详情。

### 4.2 开始解读：一个确认面板

不再把配置铺成占据主页面的多段表单。使用一个面板承载以下层次：

| 层次 | 内容 | 默认状态 |
| --- | --- | --- |
| 必须知道 | 本次解读范围、模型账户、费用归属、单次预算 | 展开 |
| 必须操作 | “确认并开始解读” | 唯一主按钮 |
| 尚未配置 | 配置个人模型，完成后返回本面板 | 按需出现 |
| 可调整 | 深入解读、指定目录、价格参数、版本比较 | “高级选项”折叠 |

默认策略建议：首次使用采用基础解读，对应现有 `quick`；用户可以显式选择深入解读，对应 `deep`。再次使用可记住上次模式，但开始前必须展示实际范围、模型与预算，不隐式提高费用上限。

这里存在取舍：`quick` 当前没有多轮深入调查，可能不足以支持完整业务链路。基础版展示“核心场景及已知证据”，不承诺每条调用关系都完整；第二期再评测是否需要调整默认分析策略。不能为了主打链路，在界面上掩盖分析深度差异。

价格来源不明确时不得显示虚假的精确估价；显示“估算依据待确认”，在高级选项提供价格配置。用户设置的预算不得被默认值覆盖。

### 4.3 项目详情：报告优先

首次无报告时呈现“源码已保存，开始解读这个项目”；已有可读报告时直接进入报告，不让配置、广告横幅或费用收据挡住内容。

建议只保留一层阅读导航：

- **读懂项目**：用途、核心场景、优先阅读入口。
- **源码与模块**：模块职责、文件树、全部证据。
- **待核实问题**：有依据的问题线索、影响、下一步验证。

删除地图三模式与报告四标签同时作为主导航的安排。地图能力仍可复用，但只在对应任务下出现。

## 5. 核心报告设计

### 5.1 默认首屏的信息顺序

1. 紧凑项目标题、源码版本、报告状态。
2. 一段项目用途摘要，默认约 120～200 个中文字符，长内容可展开。
3. 一个主要业务场景，显示“它怎样完成这件事”。
4. 直接的“查看源码依据”操作。
5. 向下延伸到“建议先读的 3 个位置”和“值得核实的线索”。

范围受限、报告过期或结果不确定等警告必须可见，但只说明影响与下一步；具体技术原因放入详情。

桌面布局建议：

```text
项目名称 · 当前源码版本                    历史报告  更多
一句业务说明 + 静态分析边界
──────────────────────────────────────────────────────
读懂项目        源码与模块        待核实问题

这个项目解决什么问题
简洁业务摘要

核心场景：用户发起一次操作                   切换场景
场景说明 / 有依据的步骤          │  当前证据
选中步骤的职责、输入输出         │  文件路径、行号
未知环节明确标出                 │  高亮源码片段
──────────────────────────────────────────────────────
建议先读的 3 个位置              查看全部阅读建议
分析详情 · 费用摘要 · 关联实训
```

这是一种布局契约，不要求在首屏硬塞下所有内容。桌面以 1440×900 验证：无需先滚过大型介绍区，就能看到项目用途、核心场景入口和证据操作。

### 5.2 第一阶段：场景与源码联动

直接利用已有 `flows` 数据，每次展示一个业务场景：标题、简洁说明、引用列表。用户选择引用，在右侧证据面板打开相应行段；已有查看源码能力可先用抽屉承接。

- 没有引用：不允许把该内容作为已证实的实现呈现。
- 一个场景有多个引用：按报告已有次序排列，不推断为真实调用顺序。
- 仅共同引用同一文件：标注“共享源码依据”，不得写成“调用”。
- 点击引用需要最多一次操作看到源码；返回后保留场景、滚动位置与选中项。
- 证据面板显示同一报告对应的源码版本，不能打开另一版本同名文件冒充依据。
- 项目地图转入“源码与模块”，默认不占据报告顶部。

### 5.3 第二阶段：结构化核心链路

只有数据契约和校验补齐后，才将主要场景升级为有向步骤链。

建议新增可选字段，不替换旧报告的 `flows`：

```ts
type EvidenceFlow = {
  id: string;
  title: string;
  summary: string;
  steps: Array<{
    id: string;
    title: string;
    responsibility: string;
    symbol?: string; // 有证据时才提供方法或函数名
    input?: string;
    output?: string;
    citations: Array<{ path: string; start: number; end: number }>;
  }>;
  edges: Array<{
    from: string;
    to: string;
    relation: 'call' | 'data' | 'inferred';
    evidence: Array<{ path: string; start: number; end: number }>;
    explanation: string;
  }>;
  gaps: string[];
};
```

设计约束：

- 默认展示 3～6 个关键步骤，最多 8 个；不追求全仓库调用图。
- 步骤 ID 唯一，边必须指向存在的步骤；允许分支，不强制所有项目是线性流程。
- 调用／数据关系必须有与关系直接相关的已读证据，不能仅凭“两文件都被读过”通过。
- 推断关系使用虚线并显示“待核实”；缺失上下文放入 `gaps`，不补造调用。
- 文件路径和行号校验只证明出处有效，不能独自证明语义关系成立；另做人工标注样本评测。
- 新结构无效时降级为一期场景视图，不让整份合法报告失败。
- 不为每个节点额外发起模型调用；优先复用已有合成请求，并评估增加字段后的输出长度与费用。
- 旧报告不后台重算、不静默收费。没有新字段就使用一期呈现。

### 5.4 阅读建议与问题线索

阅读入口默认显示 3 项，每项包含“读哪里、为什么、读完应理解什么”，超过 3 项通过“查看全部”展开，不丢弃原数据。

问题线索默认显示少量高价值项，优先依据证据充分程度和实际影响排序，不单凭模型自报的 `high` 抢占注意力。每项呈现：观察、影响、源码依据、建议验证动作、是否待核实。

没有问题时写“当前已读范围未形成明确问题线索”，不能写“项目没有问题”。AI 不自动给学生打分，不把静态观察称为已确认漏洞。

## 6. 分析过程与失败恢复

### 6.1 用户只看三阶段

| 用户可见阶段 | 可归入的内部事件 |
| --- | --- |
| 识别项目结构 | 建图、入口选择、读取初始文件 |
| 追踪核心业务 | 调查、搜索、补充阅读 |
| 整理解读与源码依据 | 合成、反证复核、引用检查 |

阶段映射要有明确的前后关系，避免内部事件交错导致界面反复倒退。显示实际已用时间，不伪造百分比，也不把当前配置的超时时间冒充预计完成时间。

### 6.2 状态与用户动作

| 展示状态 | 页面反馈 | 主动作 | 费用处理 |
| --- | --- | --- | --- |
| 已保存，未解读 | 源码可读，可稍后配置模型 | 开始解读 | 保存不调用模型 |
| 排队／运行中 | 当前阶段、已用时间 | 查看进度；有权限时可停止 | 提示已发出的调用可能收费 |
| 报告可读 | 用途、场景、证据 | 查看核心场景 | 紧凑费用摘要 |
| 报告可读但范围受限 | “部分补查未完成”，具体范围说明 | 阅读已有结果 | 不自动再次付费 |
| 失败且没有合法报告 | 简洁原因、源码和历史报告保留 | 查看历史报告／调整后重新解读 | 明确可能已有消耗 |
| 连接中断，结果未知 | “暂时无法确认状态” | 重新连接查询 | 禁止自动重发分析 |
| 已停止 | 保留事件与用量记录 | 阅读历史／重新确认后分析 | 不是退款或零费用承诺 |

必须区分“前端暂时连接不上”与“后台分析失败”。前端断线不能直接将服务端任务标失败，也不能自动创建新任务。

### 6.3 稳定性不能靠隐藏错误

- 可规范的字段在本地处理，不新增模型调用。
- 可选补查计划无效可以降级，报告保留显著限制，相关线索降为待核实。
- 原始导入无有效源码、未经授权、关键引用无效、最终报告无法校验、预算不足等不可伪装成功。
- 传输超时或回执未知不得自动重复计费请求。
- 技术详情保留阶段、错误码和安全字段诊断；不保存 API Key 或未经脱敏的模型全文作为诊断。
- 降级后的“成功”不能计入完整报告成功率；必须独立统计受限报告率和实际可读质量。

使用任务生命周期字段表达运行状态，使用 `reportQuality: complete | limited`、机器可读原因代码和 `analysisWarnings` 表达报告质量，避免通过匹配中文文案识别业务状态。2026-10-17 已确认质量契约存在，后续重点是持久化、历史兼容、UI 与评测统计的一致性验收；旧报告缺少质量记录时标为未知，不补写“完整”。这里的完整仅表示未走已知受限路径，不代表全仓库覆盖、结论必然正确或项目运行正常。

## 8. 视觉、移动端与可访问性

沿用现有纸色背景、深墨文字和克制的强调色，不再叠加新的风格体系。重点不是换配色，而是减少层级、稳定控件、把证据放在解释旁边。

- 主内容宽度建议 1120～1280px，项目标题不使用过大的宣传字号。
- 报告内容以无框分区为主；边框用于证据、状态与需要操作的区域，避免卡片套卡片。
- 同一区域仅有一个高强调主动作；次要操作用低强调按钮或文本。
- 源码字体使用等宽，路径允许换行或中间省略并可查看全文，不能撑破页面。
- 桌面宽屏使用说明与证据双栏；窄屏先说明、后证据抽屉，避免两个独立长滚动区。
- 手机使用竖向步骤，不横向缩小整张关系图；允许源码区域自身横向滚动，但页面不横向溢出。
- 引用、场景、标签和抽屉支持键盘操作；关闭抽屉后焦点回到触发控件。
- 关键控件触达区域至少 44×44px；状态不只依赖颜色；普通正文目标对比度不低于 4.5:1。
- 减少动态效果设置生效；轮询更新不重置当前场景、源码位置或键盘焦点。

针对“代码更新但运行实例未更新”和端口冲突等风险，发布不能只以构建成功为依据：

1. 明确目标实例的网页端口、API 代理、数据库目录和业务版本。
2. 确认没有进行中的付费分析，再安排重启；不为发布随意中断用户请求。
3. 新实例必须验证实际 HTTP、健康状态、鉴权后的项目接口及原项目记录。
4. 建议增加非敏感的构建版本／启动版本标识，便于确认前后端一致；不能泄露环境变量和凭据。
5. 浏览器从用户真实入口完成导入、确认、阅读与源码联动，不能仅验直达接口。
6. 真实付费验收单独确认预算和范围，不在自动回归中使用个人密钥。

## 10. 分期实施与交付门槛

以下工期仅为单开发者熟悉代码、评审及时的粗估，不是承诺。先交付第一阶段，再依据测试决定第二阶段范围。

| 阶段 | 交付内容 | 粗估 | 完成门槛 |
| --- | --- | --- | --- |
| P0：可靠性与基线 | 固定验收实例、整理故障样本、状态分类、补齐基本测试 | 1～2 个工作日 | 可重复启动、项目数据保留、错误可诊断 |
| P1：产品收敛 | 导入与确认流程、单层报告导航、场景引用联动、紧凑进度和详情 | 3～5 个工作日 | 不更改报告契约即可完成核心阅读闭环 |
| P2：证据链路 | 可选步骤契约、关系校验、链路视图、旧报告降级 | 3～5 个工作日 | 关系不靠猜测，失败可回退场景视图 |
| P3：实测与收尾 | 代表样本评测、师生可用性验证、移动端、真实费用验收 | 1～2 个工作日 | 达到验收指标，交付回滚和验证记录 |

第一阶段应优先完成“进入项目就能读懂并查看证据”，而不是先做更复杂的可视化。若时间紧，仅发布 P0＋P1，不宣称已具备有证据的调用链。

各阶段单独提交、单独验证；新链路用可选字段和功能开关灰度。回滚关闭新视图仍能读取原报告，不删除新产生的记录，也不触发自动重分析。

### 10.1 可执行工作包与依赖

以下编号用于实施和验收追踪；责任列为职责分工，不代表已经分配人员。进度记录须逐项标注“未开始／进行中／已验证／受阻”，并附证据，不能仅以组件存在判定完成。

| REL-02 | P0 · 前后端 | 完整／受限／失败／连接未知的区分，付费防重 | 超时、双击、刷新、双标签页测试；无重复分析请求 |

### 10.2 发布与回滚决策

- **首发门槛：** 保存不收费、开始前确认、证据同版、旧报告可读、连接未知不重发，五项任一失败即不发布。
- **链路开启门槛：** 结构与语义反例通过、支持范围明确、降级路径可读、无逐节点新增调用，并完成固定样本的人工核验。现有静态验证能力不应被推广为所有语言和动态调用的通用证明。
- **灰度策略：** 先使用获准公开的固定样例，再在明确参与范围内开启；首次真实调用前单独确认预算。观察完整、受限、失败分类及费用变化，不只看总成功率。
- **停止条件：** 出现越权访问、错版源码、虚假确定性关系或重复计费请求，立即停止扩大范围，关闭受影响能力并保留诊断证据。
- **回滚验证：** 关闭新链路生成与展示后，既有场景和全部引用仍可读；配置变更按部署方式重新构建或重启，先确认无进行中的付费任务。不得删除报告、重置数据库或自动重算来完成回滚。

## 11. 验收标准与测试矩阵

### 11.1 可直接判定的交互标准

- [ ] 无模型账户时仍可保存项目，保存不产生模型请求。
- [ ] 从选定文件到提交解读，默认流程不要求展开高级选项。
- [ ] 费用账户、模型与预算在最终确认前可见，不藏入高级设置。
- [ ] 同一页面区块只突出一个主动作，已有项目无需先经过宣传区。
- [ ] 点击引用一次即可查看同版源码行段；返回不丢场景与阅读位置。
- [ ] 报告默认只有一层阅读导航，不出现两套用途重叠的主标签。
- [ ] 受限报告有显著提示，且具体缺口可读，不伪装完整成功。
- [ ] 重分析失败不遮蔽可用历史报告，历史报告标明版本。
- [ ] 页面重连只查状态，不自动重新提交付费调用。
- [ ] 当前端或后端未启动时，连接故障文案不指责用户 API Key。

### 11.2 必跑测试

| 类别 | 样本／操作 | 验证点 |
| --- | --- | --- |
| 文件导入 | ZIP、文件夹、超限、空源码、含敏感配置 | 控件不串绑、限制与忽略原因准确 |
| 账户 | 未配置、有效配置、失效凭据、无权限 | 不代付，不越权，不把配置问题伪装为项目错误 |
| 正常报告 | 有场景、有引用、有问题；无问题 | 读懂项目与证据联动完整 |
| 旧报告 | 无新链路、无警告字段 | 正常兼容，无需重算 |
| 模型格式 | 数字字符串、空列表、错误对象、损坏 JSON | 安全规范或有限降级，不无限重试 |
| 真实性 | 编造路径、未读行号、无依据调用关系 | 拒绝错误引用／关系，不生成虚假图 |
| 网络与预算 | 超时、回执未知、断线、达到预算 | 不重复收费，保留真实状态与已知用量 |
| 并发 | 双击开始、刷新、两个标签页 | 不重复建立分析；操作权限一致 |
| 响应式 | 1440×900、768×1024、390×844、320×740 | 主操作可见，页面无横向溢出，源码可读 |
| 无障碍 | 键盘、焦点恢复、放大、减少动态效果 | 无键盘陷阱，状态可感知 |
| 发布 | 重启前后同一项目及报告 | 数据保留，前后端版本与代理一致 |

先运行静态检查、构建及受影响单元／集成测试，再跑真实点击的浏览器测试。直接给隐藏 input 赋文件不能代替点击“选择 ZIP”的验收；仅校验 JSON 字段不能代替报告可读性验收。

### 11.3 产品效果指标

先记录改造前基线，再比较；以下为建议目标：

| 指标 | 定义 | 建议目标 |
| --- | --- | --- |
| 核心价值理解 | 用户能说出“帮助读懂项目，并能查看依据” | 小规模试测至少 4/5 人，无额外解释 |
| 核心任务成功 | 找到一个场景并打开对应源码 | 至少 4/5 人在 60 秒内完成 |
| 首次配置负担 | 默认流程展开高级选项的必要次数 | 0 |
| 默认视觉复杂度 | 同时展开的主要内容区相对基线 | 减少约 40%，不删必要费用／风险信息 |
| 完整报告率 | 完整报告数 / 有效分析数 | 与受限报告率分别报告，不混合抬高 |
| 可读结果率 | 完整＋明确受限报告 / 有效分析数 | 在固定评测集上改善，不能以牺牲证据质量换取 |
| 安全与真实性 | 越权源码、伪造引用、未知调用自动重试 | 回归测试中 0 容忍 |

建议试测至少覆盖学生和教师两类用户；样本小，只作方向性判断，不外推统计结论。记录失败类型、用户犹豫点和任务耗时，不采集源码正文、密钥或完整模型回复作为埋点。

指标口径应在改造前冻结，避免通过调整分母制造改善：

- 分析任务按服务端任务 ID 去重；刷新、重连和重复点击不是新样本。
- 完整／受限／失败以终态分别计数；未结束任务单列，不提前算成功。用户主动停止、鉴权拒绝、导入拒绝分别报告，并说明是否进入相应指标分母。
- 同时报告“全部已接受任务”的结果分布与“固定评测集”的质量结果；不要只展示剔除失败后的模型成功率。
- 时间拆为导入耗时、等待报告耗时、找到证据耗时；网络等待与用户操作困难不能混为一个数字。
- 自动化验证、人工试测、真实模型评测分栏记录。建议每条记录包含版本、样例、模式、预期、实际结果及证据位置，不记录密钥和源码正文。

模型评测集建议包括前端、后端、全栈和脚本项目，以及缺文档、代码不完整、超大目录等反例。固定项目版本与模式；记录每次费用、完整／受限／失败分类及人工证据评分。真实模型结果具有波动，不能拿一次成功作稳定性证明。

### 11.4 五人可用性试测脚本

建议邀请至少 3 名学生、1 名教师和 1 名未参与开发的同伴；有重叠身份时按实际记录。每人约 15～20 分钟，使用获准展示的固定项目与预生成报告，不要求现场付费。主持人只读任务，不提前告诉入口位置；需要提示才能完成的任务记录为“辅助完成”，不计入独立完成率。

| 任务 | 给参与者的话 | 观察与通过条件 |
| --- | --- | --- |
| 理解价值 | “看看这个页面，说说它能帮你做什么。” | 不解释产品定位，能说出项目理解与源码依据两点 |
| 导入与费用认知 | “保存这份项目，准备解读，但先不要开始。” | 能选择正确文件、到达确认；知道保存不收费，知道下一步账户与预算 |
| 找到核心实现 | “找到一项主要功能，并给我看实现它的代码。” | 从报告就绪计时，60 秒内独立打开相关同版源码；能说明引用支持什么 |
| 理解受限状态 | “这份报告有一部分没完成，你现在可以做什么？” | 知道已有内容可读、哪些结论待核实、系统不会自动再次收费 |
| 从失败恢复 | “最新一次解读失败了，请找到上次结果。” | 能打开历史报告并辨认版本；不被迫重新上传或重跑 |

记录模板：参与者匿名编号、角色、页面构建版本、样例版本、任务、耗时、独立／辅助／未完成、首次误操作、原话反馈、问题严重度。屏幕录像需参与者同意，并避开个人密钥和非公开源码。

整改优先级：费用误解、错误版本、不可恢复的阅读阻断为发布阻断项；频繁找不到源码入口为高优先级；装饰、间距偏好在主流程问题之后。样本不足五人时如实报告，不用自动化脚本充当真实参与者。

### 11.5 结果质量评阅与指标口径

固定至少六类样本，每份列出预期业务解释、关键引用、禁止断言和已知缺失。自编合成样本适合验证反例，但不能单独证明真实项目理解能力；另选有公开许可或明确授权的真实项目，由熟悉该项目且未撰写报告的人核对。

- 每个核心结论检查三点：出处是否有效、源码是否支持该结论、措辞是否超出已读范围。任一不满足就记录具体反例，不以总分掩盖核心错误。
- 调用边另核对实际符号与调用关系；“两个文件都被引用”或行号存在不能作为通过依据。缺证据时退回场景说明。
- 完整报告率 = 完整终态任务 / 全部已接受且已终止任务；受限、失败、主动停止分别报告。历史质量未知单列，不能归入完整。
- 排队及运行中任务、计划中未执行样本单列；分母为零显示“不适用”，不显示 100%。另给出固定评测集的结果，不能事后只保留成功样本。
- 已接受任务消耗中的未知费用单列；展示已知费用小计时明确其不等于总费用。真实性、语义正确性与任务状态分别报告。
- 真实模型验证先锁定模型、模式、样本哈希、次数与总预算；达到预算即停止。单次通过不代表稳定，人工标注也不能由同一生成模型自行签收。

建议复用[源码解读评测协议](../../eval/source-reading-protocol.md)记录结果；产品评审只引用真实已执行的数据。没有历史基线时先报告当前绝对值，不宣称“提升百分之多少”。

## 12. 答辩与演示路线

建议准备一份已分析成功、可公开展示的样例，避免把演示成败押在现场付费调用和网络延迟上；明确说明它是预生成报告，不伪装实时结果。

90 秒演示顺序：

1. **15 秒：说用途。** 打开项目，看到“解决什么问题”。
2. **30 秒：讲场景。** 展示一次核心业务操作的实现说明。
3. **25 秒：核对证据。** 点击文件行号，定位源码，解释为何支持该结论。
4. **20 秒：带入学习。** 展示优先阅读位置或一个待核实问题，再说明如何关联实训。

演示中心不是“模型思考了多少轮”，而是“一个不了解项目的人，如何快速理解并能自己核对”。

## 13. 风险、非目标与待确认项

### 13.1 主要风险

- **过度简化隐藏费用**：用分层披露减少负担，不删最终费用确认。
- **地图更漂亮但不真实**：一期不画调用边，二期必须有结构与证据；未知保持未知。
- **受限报告泛滥**：单独统计受限率，查明原因，不能长期以降级掩盖模型质量问题。
- **默认基础模式特色不足**：通过真实项目评测确定场景阅读是否足够；有证据后再调整默认策略。
- **长文本迁移后丢内容**：缩略只影响呈现，完整正文、证据与历史记录仍可访问。
- **拆组件引入回归**：先建立当前行为测试，按用户流程逐段替换，不同时重构权限与状态机。

### 13.2 本轮明确不做

- 通用 AI 聊天、全仓库可编辑关系图、自动运行项目或自动修复代码。
- AI 自动评分、风险排名、未经人工确认的漏洞结论。
- 为“简洁”取消源码保存、历史版本、费用记录、受限提示和授权边界。
- 自动重跑旧报告、替用户购买模型额度、将测试结果包装成真实模型验收。

### 13.3 建议确认的产品选择

以下均为本方案推荐值，实施前确认即可，不需要继续扩展大量设计分支：

1. 模块名采用“AI 项目解读”，内部 API 与路由保持不变。
2. 首次默认基础解读，深入解读放高级选项；费用始终显式确认。
3. 首先交付一期场景证据联动，结构化调用链作为二期能力。
4. 技术详情收进单一入口，受限提醒和费用摘要仍保持可见。
5. 保留平台教学定位，但项目报告不重复承担教学宣传。

## 14. 完成定义

本次优化完成，不是“页面变得更好看”，而是同时满足：

> 新用户不需要理解分析引擎就能开始；拿到报告后，能讲清一个核心场景并找到依据；遇到局部问题仍能继续阅读可信成果；不知道的内容明确标出；费用、权限和历史数据始终受保护。

建议以 **P0＋P1 为首个可发布版本**。先证明易用性和价值表达确实改善，再投入结构化链路，而不是继续增加同屏功能。
